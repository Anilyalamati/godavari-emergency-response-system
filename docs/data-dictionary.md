# Stage 2–3 data dictionary

All application tables live in the `public` schema and have RLS enabled. Anonymous clients receive no staff-table grants. Authenticated staff receive only the minimum table privileges needed for their role; row policies then restrict profiles, incidents, teams, reporter contacts, assignments, and configuration. No client role can directly insert, update, or delete profiles or team memberships. The server-only Supabase secret key bypasses RLS and is restricted to guarded account invitations/profile creation. No real users, contact details, service areas, reports, or operational records are present in the seed.

## Tables

| Table                | Purpose and key fields                                                                                                                                                                                                                                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `profiles`           | Maps an existing Supabase Auth `auth.users.id` UUID to a staff `role` (`ADMIN`, `OPERATOR`, `RESPONDER`), display name, `is_active` flag, and `can_access_reporter_contacts` permission. Both access flags are trusted, server-controlled profile data. The contact permission defaults to `false`. No self-registration or profile seed. |
| `zones`              | UUID, unique `zone_code`, name, description, `is_demo`, and `fictional_location_label`. No zone coordinates or real geographic boundaries are stored.                                                                                                                                                                                     |
| `teams`              | UUID, unique `team_code`, name, non-empty `capabilities` text array, and fictional-demo marker/label. Demo teams do not imply real personnel or service availability.                                                                                                                                                                     |
| `team_zone_coverage` | Normalized many-to-many service-area join with `team_id` and `zone_id` FKs and a `covered_since` `timestamptz`; composite primary key prevents duplicate pairs.                                                                                                                                                                           |
| `team_memberships`   | Composite key of `team_id` and `profile_id`; stores a `LEAD`/`MEMBER` role, active flag, and join time. No memberships are seeded. Only narrow administrator operations may change another person's memberships; direct client writes and self-management are denied.                                                                     |
| `incidents`          | UUID, category, priority, status, short summary, `reported_at`, timestamps, optional location fields and `zone_id`, fictional-demo marker, optional idempotency digest, and optional tracking-token digest. No reporter-contact columns.                                                                                                  |
| `reporter_contacts`  | Separate one-to-one contact record for an incident, with optional name, E.164 phone, email, contact preference, and timestamps. No contact records are seeded. Read access requires both the explicit profile permission and the same incident/team scope as the related incident.                                                        |
| `assignments`        | UUID, incident/team FKs, optional assigning staff profile, controlled assignment status, assignment time, mandatory acknowledgement deadline, and optional acknowledgement time. Responders can read only assignments for their active team memberships. No assignments are seeded.                                                       |
| `incident_events`    | UUID, incident FK, optional actor profile, controlled event type, optional before/after incident status for `STATUS_CHANGED` only, and `occurred_at`. No free-text event field that could mix reporter contact data into the operational event log. Incident visibility follows the role/team incident policy.                            |
| `configuration`      | Text key, JSON object value, description, optional updating staff profile, and `updated_at`. Administrator-only and must contain non-secret configuration.                                                                                                                                                                                |

UUID primary keys use `gen_random_uuid()` unless the seed supplies a fixed fixture ID. All stored temporal fields are `timestamptz`; fixture timestamps include the explicit `+05:30` offset. Numeric latitude/longitude values are constrained to geographic ranges and must be supplied as a pair. Accuracy must be non-negative and requires coordinates. `GPS` and `MAP_PIN` location sources require coordinates; landmark/verbal/not-provided sources may omit them. Every demo incident must set `location_is_fictional = true`.

## Controlled values

The `incident_status` enum is exactly `REPORTED`, `UNDER_REVIEW`, `ASSIGNED`, `ACKNOWLEDGED`, `EN_ROUTE`, `ON_SCENE`, `RESOLVED`, `CLOSED`, `DUPLICATE`, and `CANCELLED`. PostgreSQL rejects any other value. The other enums are `incident_category` (`MEDICAL_ASSISTANCE`, `CROWD_SAFETY`, `LOST_PERSON`, `INFRASTRUCTURE`, `OTHER`); `incident_priority` (`LOW`, `NORMAL`, `HIGH`, `URGENT`); `location_source` (`GPS`, `MAP_PIN`, `LANDMARK`, `VERBAL`, `NOT_PROVIDED`); `staff_role` (`ADMIN`, `OPERATOR`, `RESPONDER`); `team_membership_role` (`LEAD`, `MEMBER`); `assignment_status` (`PENDING`, `ACKNOWLEDGED`, `DECLINED`, `COMPLETED`, `CANCELLED`); `reporter_contact_method` (`PHONE`, `SMS`, `EMAIL`, `NONE`); and event types `REPORT_CREATED`, `STATUS_CHANGED`, `PRIORITY_CHANGED`, `ASSIGNMENT_CREATED`, `ASSIGNMENT_ACKNOWLEDGED`, `LOCATION_UPDATED`, `CONTACT_UPDATED`, `DUPLICATE_LINKED`, and `DEMO_SEEDED`.

Priorities are stored categories, not an automated triage decision. Nothing in this prototype scores a report, selects a response, or promises assistance.

## Stage 3 role and row-access rules

- `profiles.is_active` must be true for the current profile to resolve as staff. A user may read their own profile; an active administrator can read the staff directory. User roles are loaded from this trusted table, not from Auth metadata.
- Operators can read operational incidents. Responders can read an incident only when their active membership and a pending/acknowledged assignment connect it to one of their teams. Administrator status does not grant incident access.
- Reporter-contact rows are visible only if `can_access_reporter_contacts` is explicitly true and the same user can read that incident. The default permission is false. Reporter contacts are never embedded in the standard incident list API.
- Active staff have read-only team, zone, and service-zone lookup. Only administrators can read/update `configuration` or manage staff through the protected API and narrowly guarded RPCs.
- Browser roles have no direct profile or team-membership DML privileges. Admin profile/membership RPCs verify the actor role, require another target profile, and cannot change the caller's own role or memberships. Public/anonymous users have no staff-page or staff-data access.

## Tokens, contact data, and synthetic rows

The only token-related columns are `idempotency_key_sha256` and `public_tracking_token_sha256`; both are nullable `bytea` values constrained to 32 bytes. The trusted server must generate high-entropy inputs, hash them using SHA-256 before insertion/lookup, and never log the raw value. Raw tracking/idempotency token columns do not exist. The public incident UUID is not a tracking secret.

The seed contains exactly five zones, three fictional teams, six fictional service-zone coverage links, three synthetic incidents, three synthetic `DEMO_SEEDED` events, and one non-secret demo label. It deliberately contains zero profiles, memberships, reporter contacts, and assignments. Every demonstration zone and incident has a prominent fictional label; demo incident coordinates are `NULL`. Repeated seed execution updates these fixed UUID/key records with the same values instead of creating duplicates.

## Indexes and integrity

Unique or primary-key indexes cover fixture identifiers, role/key columns, reporter contact per incident, the team/zone relation, and non-null token digests. Work indexes cover team memberships by profile, incidents by state/report time and zone/report time, assignments by incident/state and team/deadline, and incident events by incident/time and actor. Foreign keys use `RESTRICT` for references whose removal would invalidate zone/team history and `CASCADE` for dependent join/incident/contact/event rows. Staff references use `SET NULL` where the audit record remains meaningful after account removal.

Check constraints validate nonblank bounded labels, supported coordinate pairs/ranges, non-negative accuracy, demo labeling, 32-byte digests, acknowledgement deadlines, contact formats, JSON-object configuration, and consistency of status-change events. Invalid incident states and foreign keys are rejected by PostgreSQL. Stage 3 keeps RLS enabled for every table and adds narrow role policies without widening anonymous access.
