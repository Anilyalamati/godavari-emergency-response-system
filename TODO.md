# Stage 2 — Database foundation

- [x] **Versioned Supabase/PostgreSQL schema.** Create version-controlled migrations for `profiles`, `zones`, `teams`, `team_memberships`, `incidents`, `reporter_contacts`, `assignments`, `incident_events`, and `configuration`. Use UUID primary keys where appropriate, timezone-aware timestamps, foreign keys, indexes, and check constraints. Separate reporter contact details from operational incident data. Store location source, coordinates when supplied, accuracy when available, landmark, zone, and location capture time. Store incident category, priority, status, and reported time. Store assignment acknowledgement deadlines. Prepare an idempotency key for public submissions. Do not store raw public tracking tokens. Define exactly these initial incident states: `REPORTED`, `UNDER_REVIEW`, `ASSIGNED`, `ACKNOWLEDGED`, `EN_ROUTE`, `ON_SCENE`, `RESOLVED`, `CLOSED`, `DUPLICATE`, and `CANCELLED`. Additional normalized join tables are permitted when needed for referential integrity. The migration adds normalized `team_zone_coverage` and applies on a clean embedded PostgreSQL database with Supabase role/Auth-schema stubs.
- [x] **Database access and staff provisioning.** Enable RLS on sensitive tables. Default to no anonymous direct access. Do not create broad “allow all” policies for convenience. Do not create public staff-registration flows. Document secure staff account provisioning separately. The migration revokes browser-role schema/table privileges, creates no direct client policies, and the local Supabase config disables sign-up and anonymous sign-in.
- [x] **Repeatable, clearly synthetic demonstration data.** Add five fictional demonstration zones; three fictional teams with capabilities and service zones; and a few synthetic sample incidents. Clearly mark all demonstration locations as fictional. Make seeds repeatable and ensure there is no real staff, PII, operational record, or real-world location in the fixtures. The fixed-UUID SQL seed was executed twice in one clean embedded PostgreSQL database; it leaves five zones, three teams, six coverage links, and three incidents without duplicate rows or any staff, contact, or assignment fixture.
- [x] **Database documentation.** Deliver SQL migrations, a repeatable seed script, a text-based entity-relationship diagram, a data dictionary, and database setup instructions. The controlled staff-provisioning procedure is documented separately from public registration.
- [x] **Stage 2 acceptance and boundary.** Migrations work against a clean database. Seeds can be rerun safely. Invalid foreign keys and invalid states are rejected. Anonymous clients cannot list incidents or reporter contacts. Stop after Stage 2. `pnpm db:smoke` verified these checks on embedded PostgreSQL 18.6 using local Auth/role stubs. Full Supabase CLI pgTAP execution was not available in this sandbox because the native stack reported `owner: unavailable` and no services, and Docker/Podman are absent; this limitation is recorded in `docs/build-progress.md` and no full Supabase-stack test is claimed.
